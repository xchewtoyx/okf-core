# Draft 1 — Is byte-level preservation a real requirement?

- **Status:** first-draft proposal, superseded by the documents alongside it
  in this directory (requirements draft `02-`, codebase analysis `03-`,
  milestone plan draft 2 `04-`).
- **Question examined:** okf-core's editing/patching work stream treats
  "untouched bytes of a document survive an edit byte-for-byte" as its core
  contract. Is that a requirement derived from the OKF specification and the
  real corpus, or one the project invented for itself?
- **Verdict: invented.** Neither spec version requires it, the real corpus
  contains no human-authored bytes to preserve, and the requirement's paper
  trail leads back to this project's own issue tree.

## Evidence from the specifications

The only round-trip language in either OKF v0.1 or v0.2 is §4.1:
*"Consumers SHOULD preserve unknown **keys** when round-tripping"* — a
semantic rule about not dropping fields, not a byte-level rule.

- **v0.2's own mental model is whole-document rewriting.** §5.1 justifies
  keyed footnote attribution over positional citation numbering *"because
  agents constantly rewrite these documents."* The spec's robustness
  mechanism for a churning corpus is stable semantic identifiers, not byte
  stability. It solved the problem this project has been solving — at the
  data-model layer, not the serializer layer.
- v0.1 §9 states the permissive-consumption model exists so OKF "remains
  useful as bundles grow, get refactored, and are partially generated by
  agents." Refactoring — reformatting included — is the expected steady
  state.
- "Diffable in version control" (§1) motivates plain text over binary
  formats; it is not a mandate for minimal diffs. Canonical formatting also
  yields clean diffs after one convergence edit per file.
- **v0.2 retires constructs current work targets.** The body `# Citations`
  list is superseded by `sources:` frontmatter with footnote attribution
  (§13.1). `log.md` and `index.md` remain optional.

## Evidence from the real corpus (`xchewtoyx/rgh-sme`)

The flagship consumer is a 3,373-note zettelkasten whose rules state *"the
wiki's only reader is future agent instances… not humans browsing for
pleasure."*

- It uses okf-core for **validation only** (a SessionStart check and a git
  hook). No script calls the patch APIs. When a curator agent "extends or
  refines a note in place," it rewrites the file.
- Its wiki rules **ban `index.md` and `log.md`** as hub mechanisms that
  fight its search-and-follow-links discovery model.
- It already runs **Prettier** (`format-md.sh`, `proseWrap: always`) over
  its harness docs, with bundles excluded only "until a later pass" — the
  one real consumer is on a trajectory toward canonicalizing the corpus
  with a mature formatter.
- The fidelity corpus used by the #149 spike scored `mdformat` down for
  normalizing setext headings, mixed CRLF, and `*`-vs-`-` bullets — human
  quirks that do not occur in an LLM-written, style-governed wiki.
- Its notes already use v0.2-style `sources:` frontmatter while okf-core
  targets v0.1.

## How the invention compounded

Issue #110 — the genuinely valuable safety layer (stale-detection, atomic
writes, no-op detection, structured conflicts) — contains no byte-level
language. Byte-identity first appears in the #113/#148/#11 issue tree
("all non-citation content remains byte-identical") and was then promoted
into README contract prose. From there the logic was circular:
byte-identity was defined such that any standard serializer fails (they
normalize) → hand-rolled span/splice machinery became "necessary" → the
round-trip spikes then rejected mature libraries *for normalizing* — that
is, for failing the requirement the project invented.

Measured cost at the time of writing: ~2,900 lines of editing/parsing
machinery (`patching.py` 1,632 + `logs.py` 1,199 + inline-parser shims)
defended by ~3,900 lines of tests; 101 of 342 commits (~30%) are
review-fix commits; the log.md parser needed a bug fixed at round five of
review; CI carries hypothesis fuzzing, frozen-time enforcement, and TOCTOU
checklists largely to police offset arithmetic in parsers for file formats
the flagship consumer bans.

The prior decision record in this repo
(`docs/spikes/148-round-trip-refactor-descope.md`) was right to stop the
serializer refactor as then specified, but wrong in its stated reason
("byte-level preservation of human-authored files is the product") — it
kept the invented requirement and re-committed to the hand-rolled
machinery that exists to serve it.

## The corrected contract (sketch)

Replace "untouched bytes are preserved" with what the spec actually
implies:

1. **Semantic fidelity** — no data loss: unknown keys, key order, link
   titles, comments where cheaply possible. (Spec-required.)
2. **Deterministic, idempotent output** — parse with mature libraries,
   mutate the object/token model, re-serialize canonically;
   `edit(edit(x))` is stable and the corpus converges to canonical form on
   first touch. For an agent-maintained wiki, uniform formatting is a
   feature.
3. **Safe application** — the #110 plan/apply envelope (hash guards,
   conflicts, atomic writes, no-op detection) is real value and stays.

Under this framing the spike-identified "costs" evaporate: no `okf format`
precondition or bundle migration is needed (first edit canonicalizes —
acceptable when no human authored the bytes), and normalized YAML output
becomes documented canonical behavior rather than a regression. The #117
spike's library recommendation was sound; it was rejected against the
invented yardstick.

The refined requirements derived from this assessment live in
`02-editing-requirements.md`.
